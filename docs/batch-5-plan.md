## 0. 现状实测（决定方案的三个关键事实）

### 0.1 多事实输入当前**全部失败**，且一条都不写入

实测：

| 输入 | parse | unsafe | relation mentions | 写入 | 回复 |
|---|---|---|---|---|---|
| `猫会飞，也会游泳` | unknown | true | **2** | 0 | 这个我还没理解清楚 |
| `猫会飞，猫会游泳` | unknown | true | **2** | 0 | 同上 |
| `猫喜欢鱼，狗喜欢肉` | unknown | true | **2** | 0 | 同上 |
| `猫会飞。猫会游泳` | unknown | true | **2** | 0 | 同上 |
| `猫属于哺乳动物，哺乳动物属于动物` | unknown | true | **2** | 0 | 同上 |

根因是三处硬门限，全部在 `parser/sideEffectSafety.ts`：

```
LEGACY_SIDE_EFFECT_LIMITS = { maxInputLength: 160, maxNameLength: 64, maxRelationMentions: 1 }
INTERNAL_CLAUSE_BOUNDARY = /[,，;；。.!！?？\r\n]/u
CHOICE_OR_SEQUENCE_CUE   = /(还是|或者|或是|然后|并且|而且|同时|接着|另外)/
```

即：**任何含内部标点的输入**因 clause boundary 被拒；即使拆句后，**超过 1 个 relation mention** 仍被拒。`maxRelationMentions: 1` 是"一个 turn 只写一条事实"的硬编码表达。

### 0.2 分隔后的片段质量参差——这是本批**最大的坑**

实测每个候选片段的独立判定：

| 片段 | parse | unsafe | 说明 |
|---|---|---|---|
| `猫会飞` | statement | false | ✅ 干净 |
| `猫会游泳` | statement | false | ✅ 干净 |
| `狗喜欢肉` | statement | false | ✅ 干净 |
| **`也会游泳`** | **statement** | **false** | ❌ **解析成 `{也, 会, 游泳}`——主语是"也"** |
| `猫不会飞` | statement | false | ✅（B.7 后可教） |
| **`我不是小明`** | **statement** | **false** | ❌ 第一人称否认，必须继续拒绝 |
| `猫是什么` | query | true | ✅ 会被 query 门限挡住 |
| `猫会飞吗` | unknown | true | ✅ 被疑问门限挡住 |

**`也会游泳` 实测会被直接存储**：

```
engine.process("也会游泳") -> "已记录：也 会 游泳"
store -> ["也|会|游泳"]
```

所以"朴素按逗号切分"会立刻引入**新的静默数据损坏**：`猫会飞，也会游泳` 会写出一条以"也"为主语的事实。这正是 A.3 修掉的那类缺陷的翻版，B.8 必须正面处理。

### 0.3 跨片段的门控是缺失的

`不要记住猫会飞，猫会游泳` 这类输入，禁止语在**输入整体**上会被 `hasExplicitSideEffectProhibition` 捕获；但如果先切分再逐段判定，禁止语会留在第一个片段里，第二段仍可能被写入。因此**整体门控必须在切分之前跑一遍**。

## 1. 核心设计决策

### 1.1 原子性：**all-or-nothing（整轮拒绝），不做 partial-accept**

**决定：任一子事实不合法 ⇒ 整个 turn 拒绝，零写入。**

理由（按重要性排序）：

1. **诚实性**：partial-accept 会让用户看到"3 条成功、1 条失败"，但用户是按**一个句子**说的，他会合理认为整句被接受。A.7 刚刚建立了"回复必须与知识库真实状态一致"的契约，partial-accept 在自然语言层面仍是不一致的（哪 3 条？为什么第 4 条不同？）。
2. **安全**：门控的价值在于"拒绝可疑形状"。若允许部分通过，攻击面变成"把一条需要拒绝的事实藏在一串合法事实里"，而且用户很难察觉漏了一条。原子拒绝让绕过尝试整体失败。
3. **实现与解释都更简单**：单次 `persist()`、单一判定、单一回复，不需要为"部分成功"设计新的 outcome/render 语义。
4. **与既有语义一致**：现有单事实路径已经是"要么写入并确认，要么完全不写"。

代价：用户一句话里有一个错字就全盘重来。缓解方式见 1.5——回复必须**指名**是哪一段、为什么被拒，让用户能精确修正。

### 1.2 切分必须**先整体门控，再切分，再逐段门控**

顺序是硬性要求：

```
raw input
  1. 整体门控（在切分之前）：
       hasExplicitSideEffectProhibition(raw)   -> 拒
       hasQuestionStructure(raw) 命中疑问       -> 拒
       raw.length > maxInputLength             -> 拒
       raw.trim().length === 0                 -> 拒
  2. 切分（仅白名单分隔符，见 1.4）
  3. 段数 > maxFactsPerTurn                   -> 拒
  4. 每段独立：canonicalization -> parser -> 既有 safety gate -> （query 结果则拒）
  5. 任一段失败                              -> 整体拒（1.1）
  6. 全部通过                                -> 依次写入 -> 单次 persist()
```

第 1 步不可省：`不要记住猫会飞，猫会游泳` 若只按段判定，禁止语只出现在第 1 段，第 2 段会被写入。

### 1.3 省略主语的延续（ellipsis）——**必须显式、有界、可审计**

`猫会飞，也会游泳` 要求支持，但 `也会游泳` 本身解析为 `{也, 会, 游泳}`。两种处理方式：

| 方案 | 说明 | 取舍 |
|---|---|---|
| A. 不支持省略 | 要求每段自足：只支持 `猫会飞，猫会游泳` | 最安全，但用户明确举了 `猫会飞，也会游泳` 作为目标 |
| **B. 受限主语继承** | 段首为白名单延续词时，继承**紧邻前一段**已解析成功的主语 | 满足目标；规则显式、单跳、无歧义 |

**采用 B，并按以下硬约束收窄**：

- 延续词白名单（**显式常量，只有这三个 + 标点后紧跟**）：`也`、`还`、`同样`。
- **只能继承紧邻前一段的主语**，且前一段必须是**本轮已成功解析的 statement**；不得跨段、不得继承宾语、不得从对话 Context 继承（那会引入不可见状态依赖）。
- 继承后**重新走完整门控**：把 `前段主语 + 本段去延续词后的内容` 组成新串，再跑 canonicalization + parser + safety gate。不是"信任后拼装"，而是"拼装后再验证"。
- 去掉延续词后若剩余内容为空或无 relation → 该段失败 → 整体拒。
- 若前一段不是 statement（例如是 query）→ 本段失败 → 整体拒。
- 继承出的主语必须通过 `normalizeCapturedValue` 且非空、非第一人称（见 1.6）。

这样 `猫会飞，也会游泳` → 第二段 `也会游泳` → 去延续词得 `会游泳` → 拼前段主语 `猫` → `猫会游泳` → 正常门控 → 通过。

### 1.4 支持的连接形式（白名单，其余一律不支持）

**支持**（都是"两个完整、可独立成句的陈述并列"）：

| 形式 | 例 | 处理 |
|---|---|---|
| 全角逗号 `，` | `猫喜欢鱼，狗喜欢肉` | 切分 |
| 半角逗号 `,`（含后随空格） | `猫会飞, 猫会游泳` | 切分 |
| 分号 `；` `;` | `猫会飞；猫会游泳` | 切分 |
| 句号 `。` | `猫会飞。猫会游泳` | 切分 |
| 逗号/分号 + 延续词 | `猫会飞，也会游泳` | 切分 + 主语继承（1.3） |

**明确不支持**（保持现有拒绝，不因 B.8 放宽）：

| 形式 | 例 | 原因 |
|---|---|---|
| `而且`/`并且`/`同时`/`接着`/`另外`/`然后` | `猫会飞，而且会游泳` | 属 `CHOICE_OR_SEQUENCE_CUE`，历史上有意拒绝的推进/序列语义；放行需要单独的语义论证，不在本批 |
| `或者`/`或是`/`还是` | `猫会飞或者猫会游泳` | 选择结构：无法确定用户断言哪个，**必须继续拒绝** |
| 疑问片段 | `猫会飞，猫是什么` | 整轮含疑问 → 拒 |
| 第一人称否认片段 | `猫会飞，我不是小明` | 见 1.6 |
| 嵌套/多级分割 | `猫会飞，猫会游泳，狗喜欢肉` 超过 maxFacts 后拒绝 | 见 1.5 |
| 换行分隔 | `猫会飞\n猫会游泳` | 与 `\r\n` 同属 clause boundary，保留拒绝（用户可用标点） |
| 无标点的连写 | `猫会飞猫会游泳` | 无法可靠切分，**不得猜测**；仍按单事实解析并（因 2 个 mention）拒绝 |
| 顿号 `、` | `猫、狗喜欢肉` | 并列**主语**共享谓语，是另一类结构，需独立设计；本批不支持 |

### 1.5 硬上限（全部具名常量，集中在 `sideEffectSafety.ts`）

| 上限 | 值 | 依据 |
|---|---|---|
| `maxInputLength` | **160**（不变） | 现有值；B.8 不放大输入体积 |
| `maxFactsPerTurn` | **4** | 覆盖 `猫喜欢鱼，狗喜欢肉` 这类 2–3 条的自然表达，同时把写放大限制在常数范围内；单次 `persist()` 的成本仍是一次全量序列化 |
| `maxSegments`（切分深度） | **4**（= `maxFactsPerTurn`） | 切分不做递归：**只切一层**，切出的段不再二次切分。因此"拆分深度"恒为 1，段数上界即事实数上界 |
| `maxContinuationSegments` | **4** | 主语继承同为单跳；不级联继承（`A…，也B…，也C…` 的第二、三段都继承**第一段**的主语，而非逐段链式） |
| `maxNameLength` | **64**（不变） | 姓名路径不受 B.8 影响 |

**说明**：明确选择"只切一层、不递归"，因此不存在指数级或深度相关的复杂度；"拆分深度"这一项以恒定 1 收口，避免出现"切分再切分"的歧义与组合爆炸。

### 1.6 复用而不能绕过的门禁（逐条列出）

每个子片段**必须**独立通过下列全部检查；B.8 不新增任何"因为是多事实所以放行"的旁路：

| 门禁 | 位置 | B.8 下的行为 |
|---|---|---|
| 第一人称否认 | `understandingPlanner.isCompleteNegatedStatement`（B.7 新增） | `猫会飞，我不是小明` → 整轮拒 |
| 疑问结构 | `hasQuestionStructure` | 整轮 + 逐段都跑 |
| 选择结构 | `hasChoiceOrSequenceStructure` | 逐段跑；`或者/还是` 片段必拒 |
| 显式禁止 | `hasExplicitSideEffectProhibition` | **整轮先跑**（1.2 第 1 步），这是防绕过的关键 |
| clause boundary | `hasInternalClauseBoundary` | **逐段**跑（段内不得再有分隔符）；整轮层面按 1.4 白名单放行 |
| relation mentions | `countKnownRelationMentions` | 单事实门限保持 1；B.8 的放宽**仅限**"整轮 <= maxFactsPerTurn 个段、每段 <= 1 个 mention"，不是取消该计数 |
| 长度 | `maxInputLength` | 不变，且**逐段**也受同一上限 |
| canonicalization | `canonicalStatementTriple` | 每段独立走（含 A.3 别名归一） |
| 重复/相关检测 | A.7 的 `has` + `match` | 逐条独立计算 outcome |
| 否定可达性 | B.7 | 每段独立适用；`猫会飞，猫不会飞` 两段都合法，均写入 |
| 冲突裁决 | B.5 | **不在写入路径**；两条相反事实都落盘，由查询期裁决（保持 B.5 不变量） |

**关键不变量**：B.8 只放宽"一个 turn 可以包含几个合法事实"，**不放宽"一个事实怎样才算合法"**。

### 1.7 多事实的反馈语义（重复 / related / negated conflict）

每段独立计算 A.7 的 outcome（`added` / `already-known` / `related-known`），但**回复必须按段汇报**，且必须与最终知识库状态一致（延续 A.7 的契约）。

需要的结构性变更：新增一个**只读的汇总**响应形态，例如

```ts
| { readonly kind: "learned-many"; readonly results: readonly LearnedFactResult[] }
```

其中 `LearnedFactResult = { record, outcome, relatedExisting? }`。要点：

- 这是 **type-only** 变更（`types/personality.ts`），不新增运行时导出，70 exports 不受影响；`personality/registry.ts` 的穷尽性检查会强制两个 persona 都实现它。
- **歧义必须消除**："重复"与"related"是**段内**概念。同一轮里两段教同一条（`猫会飞，猫会飞`）时，第二段的 outcome 取决于第一段是否已写入。因为写入是原子批量的，判定基准必须是**本轮开始时的 store 快照 + 本轮此前段的意图**，否则回复会依赖实现细节。计划采用：**按段顺序、对"快照 + 之前段"求 outcome**，于是 `猫会飞，猫会飞` = 第 1 段 `added`、第 2 段 `already-known`，且最终 store 只有 1 条——回复与状态一致。
- `negated conflict` 在写入期**不反馈为冲突**（两段都写入），只在后续**查询**时由 B.5 裁决并解释。多事实回复只说"已记录/已存在/相关"，不说"已压制"——因为写入期没有压制任何事情。

## 3. 失败回滚语义

- **内存**：逐段写入发生在**收集阶段之后**。做法是先对全部段完成"解析 + 门控 + outcome 计算"，全部通过后才真正 `store.add`。因此不存在"写了一半才发现失败"的窗口。
- **持久化**：`store.add` 全部完成后**只调用一次** `persist()`（现状是每条事实一次）。这既保证原子性（单次快照写入），也避免 O(事实数 × store 体积) 的重复序列化。
- **既有不变量**：`persist()` 失败必须表现为 turn 失败，不得返回成功——沿用现状（`saveKnowledgeStore` 抛出则 turn 抛错）。
- **无部分写入**：任何一段失败 ⇒ 不进入写入阶段 ⇒ store 与持久层都保持 turn 前状态。加测试断言 `store.all()` 与 turn 前深度相等。

## 4. 复杂度上界

| 维度 | 上界 | 说明 |
|---|---|---|
| 切分 | O(L) | 单趟扫描白名单分隔符；L = 输入长度 ≤ 160 |
| 段数 | ≤ 4 | `maxFactsPerTurn`；只切一层，**无递归** |
| 每段解析/门控 | O(1) 相对段数 | 复用现有单事实路径，段内不得再含分隔符 |
| 写入 | O(F × S) | F ≤ 4；S = 单次 `match({subject, relation})` 的成本，受 store 二级索引限制 |
| **持久化** | **O(store 体积)** | **单次** `persist()`，与 F 无关（这是把 `persist()` 移出循环的原因） |
| 总时间相对单事实 | ≤ 常数倍 | F 有硬上限 4，故不引入新的渐进复杂度类别 |

对比 A.1 已测：store 10k 事实时单次全量序列化约 2ms；因持久化只有一次，多事实 turn 的持久化成本与单事实 turn 相同。

## 5. SDK 面与导出约束

- `conflictResolver.ts`/`sourceAuthority.ts`（B.5）与 `multiFact.ts`（B.8）**均不加入** `sdk.ts` 或任何 barrel 的 `export *` 路径；`sdk.api-surface.contract.test.ts` 必须保持 70 exports 绿灯（本批前几轮已用同样方式验证）。
- `types/personality.ts` 与 `types/reasoning.ts` 是 `export type *`，新增**类型**不产生运行时导出。
- 若实现中发现 `parser/index.ts` 的 `export * from "./sideEffectSafety"` 会因新增运行时函数而增加导出，则该函数**必须**放到不被 barrel 导出的模块（例如 `parser/multiFact.ts`），与 `teachingCanonical.ts`/`textNormalize.ts` 的既有做法一致。

## 6. 测试矩阵

### 6.1 支持的形式（正向）

| 输入 | 期望 |
|---|---|
| `猫喜欢鱼，狗喜欢肉` | 2 条写入，回复逐段列出 |
| `猫会飞。猫会游泳` | 2 条写入 |
| `猫会飞；猫会游泳` / `猫会飞;猫会游泳` | 2 条写入 |
| `猫会飞, 猫会游泳`（半角+空格） | 2 条写入 |
| **`猫会飞，也会游泳`** | 第 2 段继承主语，写入 `{猫,会,飞}` 与 `{猫,会,游泳}`；**store 中不得出现主语"也"** |
| `猫会飞。它也会游泳`（代词路径） | 依赖 Context（已 enabled）；断言不产生 `{它,...}` 垃圾事实 |

| `猫会飞，猫是什么` | 疑问片段 |
| `猫会飞吗，猫会游泳` | 疑问 |
| `猫会飞或者猫会游泳` | 选择结构 |
| `猫会飞，而且会游泳` | 不支持连接词（序列语义） |
| `猫会飞，我不是小明` | 第一人称否认 |
| `不要记住猫会飞，猫会游泳` | 显式禁止（**整轮**门控，防绕过） |
| `猫会飞，猫不会` | 片段不完整 |
| `猫会飞，`（尾随分隔符） | 空段 |
| `，猫会飞` | 空首段 |
| `猫会飞，，猫会游泳` | 空段 |
| `猫会飞猫会游泳`（无分隔符） | 不猜测切分；按单事实处理并因 2 个 mention 拒绝 |
| `猫、狗喜欢肉` | 顿号并列主语，不支持 |
| 长度 > 160 的多事实 | 超 `maxInputLength` |
| `也会游泳`（单独输入，无前段可继承） | 无法解析出主语；**不得**存成 `{也,...}` |

**关键回归**：单独输入 `也会游泳` 必须被拒（现状会存成 `{也, 会, 游泳}`）。这条测试同时守住 0.2 的坑。

### 6.3 不变量与失败回滚

| 不变量 | 断言方式 |
|---|---|
| 原子性 | 构造"前 3 段合法、第 4 段非法"的输入，断言 `store.all()` 与 turn 前**深度相等** |
| 单次持久化 | 用注入的 `StorageAdapter` 计数 `setItem` 调用；多事实 turn 断言恰好 1 次知识写入 |
| 门禁不被绕过 | 对 6.2 每一项断言零写入 + 零 Memory 写入 |
| 与 A.7 一致 | 逐段 outcome 与最终 store 状态一致（沿用 A.7 的"回复文本匹配知识库状态"测试手法） |
| 与 B.5 一致 | 反义同轮写入后，查询时由 B.5 裁决并解释；conflicts 非空 |
| 与 B.6 一致 | 多事实不改变查询侧答案排序 |
| 不引入垃圾主语 | 遍历所有受支持输入，断言 store 中不存在主语为延续词（`也`/`还`/`同样`）或为空的记录 |
| SDK | 70 exports 绿灯 |
| 幂等 | 同一多事实输入重复两次：第二次全部 `already-known`，store 不变 |

### 6.4 边界

| 用例 | 期望 |
|---|---|
| 恰好 4 段 | 通过 |
| 恰好 5 段 | 拒绝 |
| 恰好 160 字符 | 通过（若段数与段内合法性也满足） |
| 161 字符 | 拒绝 |
| 段内再含分隔符（如某段是 `猫会飞，猫会游泳`） | 该段因 clause boundary 拒绝 → 整轮拒绝（证明"只切一层"） |
| 段全为空（`，，，`） | 拒绝 |

## 9. 本批明确不做

- 不递归切分、不做嵌套子句解析。
- 不支持 `而且/并且/同时/然后/另外` 等推进连接词（需单独的语义论证）。
- 不支持顿号并列主语、不支持省略宾语/省略谓语的共享结构。
- 不从对话 Context 继承主语（只从紧邻前段继承），避免不可见状态依赖。
- 不在写入期做冲突裁决（B.5 归属查询期，不变）。
- 不放大 `maxInputLength`、不改 `maxNameLength`、不改姓名路径。
- 不迁移历史数据。
